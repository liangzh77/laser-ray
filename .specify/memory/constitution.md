# 网页应用项目 Constitution

## Core Principles

### I. 测试驱动开发 (TDD) - 强制原则
测试驱动开发是本项目的强制要求：必须先编写测试 → 用户批准 → 测试失败 → 然后实现功能 → 重构；严格遵守红-绿-重构循环；所有功能必须具有可验证的测试覆盖。

### II. 无硬编码原则
所有代码必须实现真正的业务逻辑，禁止硬编码值、魔法数字或静态配置；业务规则应通过配置、参数或算法实现；确保代码的适应性和可维护性。

### III. 架构清晰原则
代码结构必须清晰分层：模型层负责数据表示，服务层处理业务逻辑，接口层处理用户交互；每层职责明确，避免跨层直接调用；依赖关系应单向流动，避免循环依赖。

### IV. 健壮性原则
所有代码必须具备完整的错误处理机制；输入验证、边界条件检查和异常处理是强制要求；系统应优雅处理故障并提供有意义的错误信息。

### V. 可维护性原则
代码必须具备自文档化特性：函数和类名称清晰表达意图，复杂逻辑必须有注释说明；遵循统一的代码风格和命名约定；定期重构以消除技术债务。

### VI. 可扩展性原则
设计必须考虑未来扩展：使用接口和抽象来支持新功能的添加；避免紧耦合设计，确保组件可独立替换或升级；模块化设计以支持功能的独立部署。

## 技术标准

### Web应用架构要求
- 前后端分离架构，API作为数据交互桥梁
- RESTful API设计原则，清晰的HTTP状态码和错误响应
- 响应式设计，支持多设备访问
- 前端组件化开发，提高代码复用性

### 代码质量标准
- 单一职责原则：每个函数/类只负责一个明确的功能
- 开闭原则：对扩展开放，对修改封闭
- 依赖倒置原则：依赖抽象而非具体实现
- 代码覆盖率必须达到80%以上

## 开发流程

### 开发工作流
- 功能开发必须从规格说明开始，明确验收标准
- 实现前必须编写失败的测试用例
- 每个功能分支必须独立可测试
- 代码审查必须验证对章程的合规性

### 质量门控
- 所有代码必须通过静态分析检查
- 集成测试必须验证核心业务流程
- 性能测试必须满足预定义的响应时间要求
- 安全扫描必须通过，无明显漏洞

## Governance

本章程优先于所有其他开发实践和规范；章程修改必须包含完整的文档、团队批准和迁移计划；所有代码审查必须验证对章程的合规性；复杂的设计决策必须有明确的理由说明；违反章程原则必须得到技术负责人批准并记录原因。
